## 1.8.1 (2026-11-11)
- Fix: self-edit detection in `claude-code-review.yml` read a big PR file list wrongly. The `Detect self-edit` step piped the file list into `grep -Fxq`. `grep -q` exits at the first match, so on a large PR that lists the workflow early (about 2,500 files in the reproduction, below the 3,000-file API limit) `printf` died of SIGPIPE, `set -o pipefail` made the condition fail (status 141), and the step wrote `self_edit=false`. The workflow then ran the action, which refuses to run on a PR that edits the workflow, so the PR stayed red and no `review-waiver` could clear it. It could not turn the check green falsely. Found by the Codex review of PR 18.
  - The step now matches against a here-string with a `grep` that reads all of its input: `grep -Fx '.github/workflows/claude-code-review.yml' <<< "$files" > /dev/null`.
  - Regression tests (`test/claude-review-fail-loudly.test.mjs`): a list of about 2,500 names with the workflow first (also across pages), in the middle, last and absent, each run three times against the real step script. Before the fix the first case produced `self_edit=false` in 5 of 5 runs. A guard test also fails if any workflow template pipes into `grep -q` or `grep -m`.
  - What synced repos see: a one-time `UPDATE` of `.github/workflows/claude-code-review.yml` on the next sync. Because that PR edits the review workflow, it is a self-edit PR and needs one `review-waiver: <HEAD_SHA>` comment from a repo admin, as for 1.8.0. Repos that have not synced 1.8.0 yet get both changes in one sync PR and need one waiver. Nothing else changes.

Origin: boycepoleonjr/bitburner PR 38 (sync v1.3.0 to v1.6.2) edited `.github/workflows/claude-code-review.yml`. `claude-code-action` refuses to run when the PR's copy of its workflow differs from the default branch ("Skipping action due to workflow validation"), so no summary was posted and the 1.6.0 `Verify the review was complete` step correctly failed.   - When `self_edit=true` the `Run Claude Code Review` step is skipped (it cannot run), and `Verify the review was complete` takes a self-edit branch. It passes only if an issue comment written by a human user (`user.type` User, never a bot) has a line exactly `review-waiver: <HEAD_SHA>` for the current head SHA, and its author is the repository owner (`author_association` OWNER, user-owned repos) or has the `admin` permission on the repo (a GET of `repos/<repo>/collaborators/<login>/permission`; organization owners are MEMBER, so the lookup is what lets them waive). Otherwise it fails with an `::error::` saying that the PR edits the review workflow, Claude cannot review it, an independent review is required, and a repository admin (the owner) must then comment `review-waiver: <HEAD_SHA>`. A waiver for an older SHA, or from a bot or someone without admin permission (write, maintain, triage, read), does not count. A passing waiver logs a `::warning::` naming who waived it and that no Claude review ran, never "Review complete".
  - Every other PR is verified exactly as in 1.7.0.
  - What synced repos see: the first sync PR per repo that changes `claude-code-review.yml` is itself a self-edit PR, so it needs one waiver: get an independent review of that PR, then a repo admin (the owner) comments `review-waiver: <HEAD_SHA>` for its head SHA. Any later push to that PR needs a new waiver. In sync PRs, put the workflow-file update in its own tiny PR so the rest of the sync gets a real review.

## 1.7.0 (2026-11-04)
- Policy (new STANDARD rule SUP-7): conventions never impose dependency, runtime, action or tool versions. Each repo's lockfile and Dependabot choose versions. The only exception is a major security issue (a published advisory or CVE with real exposure for us). Such an exception names the advisory, states the minimum safe version as a floor (not an exact pin), and carries a removal condition. Compatibility problems and preferences are not exceptions. Why: version pins in synced files collided with Dependabot. A forced sync reverted a Dependabot `actions/setup-node` bump in a synced repo, and the next sync would pin the old version again. Every round cost extra agent work across the repos.
- SUP-1 clarified: the pin form (full commit SHA plus a version comment) is still required. Which version is the repo's choice, and Dependabot maintains it. SUP-5 and SUP-6 were rewritten: no ecosystem has an `ignore` rule, and `actions/checkout` is no longer held at v4.4.0.
- Dependabot: the `actions/checkout` major-version `ignore` from 1.4.0 is removed (`CHECKOUT_IGNORE` in `sync.mjs`). The synced `dependabot.yml` has no `ignore` rule for any ecosystem.
- Checkout hardening without a version hold: every `actions/checkout` step in `claude-code-review.yml`, `conventions-check.yml` and `deploy-secrets-lint.yml` sets `persist-credentials: false`. Checkout then removes its auth when the step ends, so no token stays in git config (local, `include.path` or `includeIf.gitdir`) on any checkout version. That was the reason for the old hold. I checked `claude-code-action` v1.0.264's source: it sets `origin` to its own app token (OIDC exchange) before its only git network call and does not need the checkout credential. Its own cleanup only reads `include.path`, while checkout v6+ writes `includeIf.gitdir:*.path`, so `persist-credentials: false` is the fix that actually closes the gap. The other two workflows only clone the public conventions repo.
- `sync.mjs`: version refs in the three synced workflows are repo-owned after the first write (manifest `"refs": "repo"`).
  - A new file still gets the template's refs as seeds.
  - On later syncs, each `uses: owner/action@<sha> # <version>` keeps the repo's ref (matched by `uses` path) and the repo's `node-version` values. An action new to the template gets the template's ref.
  - `--check`, the lock hashes (same lock format, normalized content for these three files) and conflict detection ignore those refs. A Dependabot bump is never drift, never a `CONFLICT`, needs no `--force`, and is never downgraded.
  - Locks written before 1.7.0 still work. A file whose only change since the last sync is a Dependabot ref bump is treated as unedited.
- SHA-form guard (SUP-1): a repo ref that is not a full 40-hex SHA is drift. Sync notes it and writes the template seed in its place. A test checks that every `uses:` in the templates is a full SHA with a version comment.
- Seeds: template SHAs are seeds only. From now on, bumping a seed alone needs no conventions release and causes no `UPDATE` in synced repos. 1.7.0 keeps the 1.6.3 seeds unchanged (checkout v4.4.0, setup-node v7.1.0, claude-code-action v1.0.264); a later patch will bump them. Because sync now keeps repo refs, a repo that jumps from 1.6.2 straight to 1.7.0 keeps its setup-node ref instead of getting 1.6.3's v7.1.0; Dependabot proposes that bump.
- Upgrade edge case: a repo locked at 1.6.2 whose `actions/setup-node` ref Dependabot already bumped (for example to v6) gets a `CONFLICT` on `conventions-check.yml` and `deploy-secrets-lint.yml` ("edited by hand since last sync"). Its pre-1.7.0 lock hash matches neither the file nor the file with its refs reset to the 1.7.0 seeds, because the setup-node seed moved in 1.6.3. Fix: run `sync.mjs --repo . --force` once. With 1.7.0 `--force` writes the template but keeps the repo's refs, so it adds `persist-credentials: false` and downgrades nothing. Repos locked at 1.6.3, and untouched 1.6.2 repos, upgrade without a conflict.
- Wording: the dependency-update skill, `global/CLAUDE.md` and the synced `agents-core` block replace "if you must downgrade or pin a package" with: do not pin or cap versions to satisfy conventions or to avoid work; pin or set a floor only for a documented major security issue, and declare it in the manifest. SUP-4 (declare changes openly) is unchanged.
- What synced repos see on their next sync: a one-time `UPDATE` of `.github/dependabot.yml` (the `ignore` rule is removed), the three workflows (`persist-credentials: false`, header comment, version header), the `agents-core` block and the dependency-update skill. Their action refs and `node-version` do not change, including refs Dependabot already bumped. After that, Dependabot's checkout major PRs arrive like any other.
- Tests: `test/repo-owned-refs.test.mjs` is new. The dependabot test and the claude-review pin test now check the form, not a specific version.

## 1.6.0 (2026-11-02)
- Rule change (CI-4): the synced `claude-review` workflow now fails loudly when it cannot read the full PR diff. Origin: a PR whose combined diff was over GitHub's 20,000-line limit made `gh pr diff` return HTTP 406, yet the review job concluded success with a summary saying it only covered "what I could read".
- Large diffs: when `gh pr diff` fails for any reason, the reviewer falls back to `gh api repos/<repo>/pulls/<n>/files --paginate` (GET only) and reviews file by file from each file's `patch`. A file without a patch (binary or too large; a pure rename with nothing to read is the one exception), any failed call, or a file count that differs from `changedFiles` makes the review incomplete. That `gh api` path is added to `--allowedTools`, scoped to this PR; "GET only" is a prompt rule because the allowedTools syntax matches by prefix.
- Machine-readable result: the single summary comment now contains exactly one line, `review-status: complete <HEAD_SHA>` or `review-status: incomplete <HEAD_SHA> <short reason>`. The human summary text is unchanged.
- New last step `Verify the review was complete` (GET only, same token scopes, `GH_TOKEN` from `github.token`): finds the newest bot-authored comment that names the head SHA and carries a status line, and exits 1 with `::error::` unless it has exactly one status line and that line is `review-status: complete <HEAD_SHA>`. No summary for the SHA, a comment-list error, a malformed or duplicated status line, or an incomplete status all fail the job. Comments from humans and bot comments without a status line are ignored, so a typed status line cannot satisfy the check and a later deploy-bot comment cannot hide the summary.
- Unchanged: checkout pinned at v4.4.0, `claude-code-action` pinned by SHA, `permissions: {}` with job-level permissions, concurrency with `cancel-in-progress`, and the draft/fork/bot skips. Those skips still produce a skipped job, not a failure; documented in CI-4 that durable-agent treats a skipped required check as blocking.
- Synced repos get a one-time `UPDATE` of `.github/workflows/claude-code-review.yml` on the next sync. A PR whose review comes back incomplete now shows a red `claude-review` check until a re-run or a push produces a complete review.
- New tests in `test/claude-review-fail-loudly.test.mjs`: the status-line contract, the fallback and its tools, the pins and permissions, and the verify script run against a fake `gh` (complete, incomplete, missing, stale SHA, duplicate or malformed line, human spoof, newest-wins across pages, fetch error).

## 1.5.1 (2026-11-01)
- New rule DEP-3 (and a line in the synced `agents-core` block): deploy secrets (cloud tokens, account ids) live only in GitHub Environments restricted to specific branches (plus required reviewers where the plan allows them), never as repository or organization secrets; every job that reads them declares `environment:`. The standard notes that without required reviewers anyone who can push to an allowed branch can still read the secrets, and prefers host-side builds (for example Cloudflare Workers Builds) where available, so no deploy token lives in GitHub. DEP-1 no longer says "repo secrets". Origin: a Codex security finding on a PR whose branch workflow could read a repo-level Cloudflare token with no approval step.
- New script `scripts/lint-workflow-secrets.mjs` (dependency free): fails when a job reads `secrets.CLOUDFLARE_*` without a job-level `environment:`, when the secret appears above `jobs:`, when a `pull_request_target` workflow references it, or when `secrets: inherit` is passed to an external reusable workflow. It matches secret names case-insensitively, including `secrets['NAME']`, `toJSON(secrets)` and `secrets[<expression>]`, and fails closed on a reference it cannot attribute to a job. `--secret <regex>` widens the pattern.
- New synced workflow `.github/workflows/deploy-secrets-lint.yml` (manifest id `deploy-secrets-lint`, mode `replace`, all profiles, skippable): runs the script from the pinned conventions version on every PR and push to `main`. Synced repos get one new file on the next sync; a repo that already keeps deploy secrets in environments passes unchanged, a repo that does not will fail until it moves them.

## 1.5.0 (2026-10-25)
- New optional `dependabot_target_branch` in `.conventions.json` (unset by default). When set, every ecosystem in the synced `dependabot.yml` gets `target-branch: "<branch>"`, so repos with a staging-first flow stop getting Dependabot version-update PRs into the default branch. The grouped major PR is never merged blindly; split it and do each major with the dependency-update skill (new rule SUP-5). Source: https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference (see `groups` / `applies-to`, and `ignore`).
- Wording fix: the moving major line `v1` is a branch, not a tag (cloud sessions get 403 pushing tags). Exact `vX.Y.Z` tags are unchanged.
