# Changelog

## 1.6.1 (2026-11-02)
- Claude Code no longer adds AI attribution in synced repos. New synced file `.claude/settings.json` (manifest id `claude-settings`, new mode `json-merge`, all profiles, skippable) sets `attribution.commit` and `attribution.pr` to empty strings and `attribution.sessionUrl` to `false`, plus the deprecated `includeCoAuthoredBy: false` for older Claude Code versions. Per the settings reference, `attribution` replaced `includeCoAuthoredBy` in v2.0.62, and Claude Code ignores `includeCoAuthoredBy` once `commit` or `pr` is set, so both can coexist.
- `json-merge` is a new sync mode: the template's keys are set in an existing file, objects merge, arrays are unioned, and all other keys are kept. A missing file is created; a file that is not a JSON object is a `CONFLICT`. It is idempotent and `--check` reports drift when a managed key is missing or different.
- New line in the synced `agents-core` block: "No AI attribution in commits, PR bodies or comments." Synced repos get a one-time `UPDATE` of the block.
- Limit: these settings cover commits and pull request descriptions made by Claude Code. The docs do not say they cover comments or reviews posted through GitHub integrations or MCP tools, so a footer on such a comment may still appear.
- Tests in `test/ai-attribution-settings.test.mjs`.

## 1.6.0 (2026-11-02)
- Rule change (CI-4): the synced `claude-review` workflow now fails loudly when it cannot read the full PR diff. Origin: a PR whose combined diff was over GitHub's 20,000-line limit made `gh pr diff` return HTTP 406, yet the review job concluded success with a summary saying it only covered "what I could read".
- Large diffs: when `gh pr diff` fails for any reason, the reviewer falls back to `gh api repos/<repo>/pulls/<n>/files --paginate` (GET only) and reviews file by file from each file's `patch`. A file without a patch (binary or too large; a pure rename with nothing to read is the one exception), any failed call, or a file count that differs from `changedFiles` makes the review incomplete. That `gh api` path is added to `--allowedTools`, scoped to this PR; "GET only" is a prompt rule because the allowedTools syntax matches by prefix.
- Machine-readable result: the single summary comment now contains exactly one line, `review-status: complete <HEAD_SHA>` or `review-status: incomplete <HEAD_SHA> <short reason>`. The human summary text is unchanged.
- New last step `Verify the review was complete` (GET only, same token scopes, `GH_TOKEN` from `github.token`): finds the newest bot-authored comment that names the head SHA and carries a status line, and exits 1 with `::error::` unless it has exactly one status line and that line is `review-status: complete <HEAD_SHA>`. No summary for the SHA, a comment-list error, a malformed or duplicated status line, or an incomplete status all fail the job. Comments from humans and bot comments without a status line are ignored, so a typed status line cannot satisfy the check and a later deploy-bot comment cannot hide the summary.
- Unchanged: checkout pinned at v4.4.0, `claude-code-action` pinned by SHA, `permissions: {}` with job-level permissions, concurrency with `cancel-in-progress`, and the draft/fork/bot skips. Those skips still produce a skipped job, not a failure; documented in CI-4 that durable-agent treats a skipped required check as blocking.
- Synced repos get a one-time `UPDATE` of `.github/workflows/claude-code-review.yml` on the next sync. A PR whose review comes back incomplete now shows a red `claude-review` check until a re-run or a push produces a complete review.
- New tests in `test/claude-review-fail-loudly.test.mjs`: the status-line contract, the fallback and its tools, the pins and permissions, and the verify script run against a fake `gh` (complete, incomplete, missing, stale SHA, duplicate or malformed line, human spoof, newest-wins across pages, fetch error).

## 1.5.1 (2026-11-01)
- New rule DEP-3 (and a line in the synced `agents-core` block): deploy secrets (cloud tokens, account ids) live only in GitHub Environments restricted to specific branches (plus required reviewers where the plan allows them), never as repository or organization secrets; every job that reads them declares `environment:`. The standard notes that without required reviewers anyone who can push to an allowed branch can still read the secrets, and prefers host-side builds (for example Cloudflare Workers Builds) where available, so no deploy token lives in GitHub. DEP-1 no longer says "repo secrets". Origin: a Codex security finding on a PR whose branch workflow could read a repo-level Cloudflare token with no approval step.
- New script `scripts/lint-workflow-secrets.mjs` (dependency free): fails when a job reads `secrets.CLOUDFLARE_*` without a job-level `environment:`, when the secret appears above `jobs:`, when a `pull_request_target` workflow references it, or when `secrets: inherit` is passed to an external reusable workflow. It matches secret names case-insensitively, including `secrets['NAME']`, `toJSON(secrets)` and `secrets[<expression>]`, and fails closed on a reference it cannot attribute to a job. `--secret <regex>` widens the pattern.
- New synced workflow `.github/workflows/deploy-secrets-lint.yml` (manifest id `deploy-secrets-lint`, mode `replace`, all profiles, skippable): runs the script from the pinned conventions version on every PR and push to `main`. Synced repos get one new file on the next sync; a repo that already keeps deploy secrets in environments passes unchanged, a repo that does not will fail until it moves them.

## 1.5.0 (2026-10-25)
- New optional `dependabot_target_branch` in `.conventions.json` (unset by default). When set, every ecosystem in the synced `dependabot.yml` gets `target-branch: "<branch>"`, so repos with a staging-first flow stop getting Dependabot version-update PRs into the default branch. Per GitHub's reference, `target-branch` applies to version updates only; security updates still target the default branch.
- The value is validated (a branch name: letters, digits, `.`, `_`, `-`, `/`; no quotes, spaces or newlines) and sync exits non-zero without writing anything otherwise. An empty string means unset.
- Repos that do not set it get a byte-identical `dependabot.yml`; no sync is needed beyond the version bump.

## 1.4.0 (2026-10-22)
- Behavior change in the synced `dependabot.yml`: the `github-actions` ecosystem now ignores `actions/checkout` for `version-update:semver-major`. Checkout is held at v4.4.0 on purpose: v6+ persists the token through `includeIf.gitdir`, which `claude-code-action` does not clear, so the token would stay usable during the Claude run. This is a deliberate, narrow exception to the "no `ignore` rule" decision in 1.1.0: only `actions/checkout`, only major version updates, no other dependency or ecosystem. A security fix that ships only in a newer checkout major will not get a Dependabot PR; check checkout's releases and advisories by hand once a quarter (new STANDARD rule SUP-6) and decide whether the pin can move.
- The dependabot test now allows exactly that rule and still fails on any other `ignore`.
- Synced repos get a one-time `UPDATE` of `.github/dependabot.yml` on the next sync.

## 1.3.0 (2026-10-18)
- Behavior change in the synced `claude-review` workflow (CI-4): it now also runs on every push (`synchronize`). A newer push cancels the older run and the newer run reviews the full diff, so nothing is skipped.
- A missing `CLAUDE_CODE_OAUTH_TOKEN` now fails the job loudly (first step, `::error::` with the fix) instead of skipping the review. Repos without the secret should add it or add `claude-review` to `skip`.
- The review prompt always reviews the full PR diff, reads existing PR comments and inline review comments first (`gh pr view --comments`, `gh api .../pulls/N/comments --paginate`, GET only), does not repeat findings that are posted and still apply, and ends with one summary comment that says first review or re-review (with the head SHA) and "No new issues found" when there is nothing new. `gh api` is allowed only for this PR's review-comments path; "GET only" is a prompt rule because the allowedTools syntax matches by prefix.
- `timeout-minutes` 20 -> 30. `allowed_bots` uses double quotes so the rendered file is Prettier 3 clean; the repo's test workflow now renders the template (with and without focus) and runs `prettier@3 --check` on it.
- STANDARD CI-4 updated.

## 1.1.0 (2026-10-18)
- New synced `agents-review` block in `AGENTS.md` (after `agents-core`): "Review guidelines" with P1 blocking criteria and extra checks, read by AI reviewers and people. `sync.mjs` inserts the block into existing `AGENTS.md` files right after the previous block, leaving all other text unchanged.
- CI-4 rewritten from a PR-review benchmark: Codex GitHub app is the primary reviewer; the Claude review workflow covers every non-draft human PR with no skippable triage step, plus on-demand `@claude`; both read the Review guidelines; no self-hosted Codex workflow; Cursor Bugbot off by default.
- Dependabot: every ecosystem now has two version-update groups, `minor-and-patch` and `major`, each with `applies-to: version-updates`, so weekly updates arrive as one grouped minor/patch PR and one grouped major PR. No `ignore` rule: ignoring majors would also filter security updates per GitHub's reference. `applies-to: version-updates` keeps security updates out of the groups, so they stay separate and unaffected. The grouped major PR is never merged blindly; split it and do each major with the dependency-update skill (new rule SUP-5). Source: https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference (see `groups` / `applies-to`, and `ignore`).
- Wording fix: the moving major line `v1` is a branch, not a tag (cloud sessions get 403 pushing tags). Exact `vX.Y.Z` tags are unchanged.
